# v1.5.0 - Site Independence Architecture

**Release Date**: September 4, 2026

## Overview
This release introduces a major architectural refactoring that decouples the bot from the ttfm-socket library through an adapter pattern. The foundation is now laid for multi-site support, enabling future integrations with different chat platforms and socket servers without code duplication. This is a non-breaking change—all bot functionality remains identical while the internal architecture becomes extensible.

## Major Features

### 🌐 Adapter Pattern Architecture - Multi-Site Foundation
The bot now uses pluggable adapters to abstract external dependencies:

**Socket Adapter Pattern**:
- `AbstractSocketAdapter` - Interface for all socket implementations
- `HangFmSocketAdapter` - Hang.fm implementation (currently the only concrete adapter)
- Single point of coupling: ttfm-socket library imported only in `HangFmSocketAdapter`
- All socket operations route through high-level methods: `connect()`, `disconnect()`, `joinRoom()`, `voteOnSong()`, `removeDj()`, `skipSong()`
- Future adapters (e.g., `TwitchStreamAdapter`, `DiscordSocketAdapter`) can be added without modifying existing code

**API Adapter Pattern**:
- `AbstractSiteAdapter` - Interface for all site API implementations
- `HangFmApiAdapter` - Hang.fm implementation
- Consolidates all REST API calls for user management and authentication
- Methods: `getUserProfile()`, `updateUserNickname()`, `getChatAuthToken()`, `getAllPresentUsers()`, `getGatewayBaseUrl()`, `getAuthHeaders()`
- Future adapters can implement alternative APIs (e.g., Twitch API, Discord API)

**AdapterService Orchestrator**:
- Central service managing adapter initialization and validation
- Validates configuration before allowing bot startup
- Loads appropriate adapters based on framework configuration
- Provides clear error messages for missing/invalid configuration

**ServiceContainer Integration**:
- Adapters registered in serviceContainer during startup (`initializeAdapters()`)
- All services access adapters through `services.socketAdapter` and `services.apiAdapter`
- Adapter initialization is a critical startup gate—bot fails gracefully if adapters can't initialize

### 🔧 Refactored Services

**hangUserService.js**:
- All functions now accept `services` parameter for adapter access
- Functions: `getUserNicknameByUuid()`, `updateHangNickname()`, `getCometChatToken()`, `getAllPresentUsers()`
- Calls `services.apiAdapter` instead of making direct REST calls
- Removes direct imports of config and makeRequest utilities

**hangSocketServices.js**:
- All functions now accept `services` parameter for adapter access
- Functions: `upVote()`, `downVote()`, `removeDj()`, `skipSong()`
- Calls `services.socketAdapter` for all socket operations
- Removes ActionName constants and direct socket.action() calls

**bot.js**:
- Uses `services.socketAdapter` instead of directly importing and using SocketClient
- Event listeners (`statefulMessage`, `statelessMessage`, `serverMessage`, `error`) route through adapter
- Connection status checked via `socketAdapter.isConnected()` instead of raw socket
- Graceful error handling when socket adapter isn't available

### 📋 Configuration

**New Environment Variables**:
- `API_FRAMEWORK` - Specifies which API adapter to load (default: 'hangfm')
- `SOCKET_SERVER_URL` - WebSocket server URL (default: 'https://socket.prod.tt.fm')

See [SETTING_UP_YOUR_ENVIRONMENT.md](../SETTING_UP_YOUR_ENVIRONMENT.md) - Step 12 for full configuration details.

## Migration Guide
**No action required** for existing deployments. The bot works identically to v1.4.2. For developers extending the bot:

### Adding a New Platform (e.g., Twitch)
1. Create `src/socketAdapters/TwitchSocketAdapter.js` implementing `AbstractSocketAdapter`
2. Create `src/apiAdapters/TwitchApiAdapter.js` implementing `AbstractSiteAdapter`
3. Register in adapter loaders (socketAdapters/index.js, apiAdapters/index.js)
4. Set `API_FRAMEWORK=twitch` in environment
5. Bot initializes and uses new adapters automatically
